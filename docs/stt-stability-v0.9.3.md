## 2. 5분 녹음 처리 구조 (v0.9.3)

```text
녹음 종료/파일 선택 ─ 파일 검사(형식·25MB·20분·재생 가능) ─ 모델만 미리 준비 (다운로드·초기화, 음성 없음)
"저장하고 AI로 정리하기"
 ├ 1. 녹음 업로드 (Supabase Storage + DB 행)            ← 여기서부터 녹음은 브라우저가 죽어도 남음
 ├ 2. 작품 화면으로 바로 이동 (기다리지 않음)
 └ 3. 앱 전역 기기 작업(deviceJobs) — 화면을 옮겨도 계속
      ├ 서버에 백업 전사 작업 생성 (defer_seconds=900 → 15분 뒤에야 서버가 가져감, DB에 작업 ID·상태)
      ├ 음성 디코딩 → 무음 지점에서 ≤28초 구간으로 분할 (겹침 없음 → 중복 없음)
      ├ 구간마다 변환 → 결과를 이 기기(localStorage)에 기록 → 진행: "n/m 구간 완료"
      ├ 성공 → POST …/transcript/browser → 백업 작업 자동 취소, (동의 있으면) AI 요약 작업 + Worker 즉시 실행 요청
      └ 실패·정지·"서버에서 처리하기" → 백업 작업을 지금 처리하도록 앞당김 + Worker 즉시 실행 요청
탭이 강제 종료됨 → 다시 열면 녹음 카드: "이어서 바꾸기"(끝난 구간은 건너뜀) / "서버에서 변환하기"
                   그대로 두면 15분 뒤 서버(백업 작업)가 처리
```

- 중복 방지: 서버의 기존 잠금(녹음 행 → 진행 중 작업)과 부분 유니크 인덱스 그대로. 같은 녹음의 기기 작업은 앱 안에서 1개, 기기 변환은 한 번에 1개 녹음.
- 새로고침 후 상태 복원: 서버 상태(전사·요약 작업)는 DB에서, 기기 진행분은 localStorage에서.
- 변환 중 새로고침·닫기를 누르면 브라우저 확인 창.
- DB 마이그레이션 없음 (`ai_processing_jobs.run_after` 기존 컬럼 사용).

## 4. 대안 비교 (서버 대체 처리)

| 대안 | 속도 (5분 녹음) | 무료 한도 | 안정성 | 동시 사용자 | 개인정보 |
| --- | --- | --- | --- | --- | --- |
| **A. GitHub Actions + 즉시 실행 요청** (이번 구현) | 대기: 예약만 쓰면 **실측 5.8~29시간**. 즉시 실행 요청 시 보통 1분 안팎 시작 예상(미측정) + 준비 20~60초 + small/INT8 변환(러너에서 **미측정**) | 공개 저장소 표준 러너 무료 | GitHub가 실행 시점을 보장하지 않음 (지연·누락 사례 있음) | 실행 1개씩 직렬, 1회 최대 10건 | 음성이 GitHub(Azure) 러너에서 처리. 공개 저장소라 **실행 로그가 공개**(작업 ID·오류 코드만 기록) |

| C. 무료 한도 STT API (예: Groq Whisper) | 수 초 수준(공개 자료 기준, 미측정) | 공개 자료상 분당 20건·일 2,000건·시간당 음성 7,200초 수준 — 출처마다 다름, 공식 확인 필요 | 외부 서비스 정책·한도 변경 위험 | 한도 안에서 높음 | **음성을 새 외부 업체로 전송** → 동의서·개인정보 처리방침 변경 필요, 무료 등급 데이터 사용 조건 확인 필요 |

**권장(무료 유지)**: B(기본) + A(즉시 실행 요청으로 대체). 단, **모든 기기에서 5분 녹음을 120초 안에 처리하는 것은 무료 구조로 보장할 수 없다.** 휴대폰 WASM은 이 PC에서도 약 1배속이었고, A는 GitHub 실행 지연을 없앨 수 없다. 보장이 필요하면 C(외부 전송 동의 변경 필요) 또는 D(유료) 중 하나를 **승인 후** 도입해야 한다.

## 5. 측정

### 5.1 실측 (2026-11-12, 개발 PC: Windows 10, Chrome 157 headless, WASM base = 휴대폰 기본 경로와 같은 설정)

음성: Windows 한국어 TTS(Heami)로 만든 미술 첨삭 문장 — **실제 학원 녹음이 아님**. CER = 정답 대본 대비 글자 오류율(공백·문장부호 제외). 메모리 = 테스트 Chrome 프로세스 전체 작업 집합 최대값.
측정 중 같은 PC에서 백엔드 DB 테스트가 함께 돌고 있었다(속도가 다소 느리게 나왔을 수 있음).

| 음성 | 상황 | 모델 파일 받기 | 세션 초기화 | 변환 | 구간 | 전체 | CER | Chrome 메모리 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 19.7초 | 첫 실행(다운로드) | 10.2초 | 17.3초 | 32.5초 | 1 | **61.0초** | 3.1% | 1,257MB |
| 40.7초 | 모델 재사용 | 0 | 0 | 54.4초 | 2 | **55.0초** | 5.6% | 1,222MB |
| 61.7초 | 모델 재사용 | 0 | 0 | 61.7초 | 3 | **62.1초** | 4.4% | 1,092MB |

- 1분 이하 목표(60초): 첫 실행 20초 음성 61.0초, 1분 음성 62.1초 → **경계에서 약간 넘음** (이 PC 기준). 휴대폰은 더 느릴 것으로 예상.
- 3분·5분: 측정 도중 **PC 메모리 부족으로 측정 프로세스가 강제 중지**되어 결과 없음. 위 속도(약 1배속)로 보면 5분 음성은 약 5분 걸려 **120초 목표를 넘을 가능성이 높다**.

## 7. 남은 기기별 한계

- 휴대폰 WASM은 단일 스레드(교차 출처 격리 미적용)라 느리다. 5분 녹음은 수 분 걸릴 수 있다.
- iPhone Safari는 메모리 정보(deviceMemory)를 주지 않아 항상 WASM. 메모리 한도가 작은 기기는 여전히 탭이 종료될 수 있으나, 녹음은 먼저 저장되고 "이어서 바꾸기"/서버 백업으로 복구된다.
- 백그라운드 탭에서는 브라우저가 Worker를 늦추거나 멈출 수 있다 → 백업 작업이 15분 뒤 서버에서 처리.
- 기기 진행분은 그 기기의 localStorage에만 있어 다른 기기에서는 이어서 할 수 없다(서버 백업은 가능).
