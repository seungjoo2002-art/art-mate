### 실기 유형과 작업 목적을 분리한 이유

'기초디자인'은 무엇을 그렸는가(실기 유형), '모의시험·개인 연습'은 왜 그렸는가(작업 목적)입니다. 한 필드에 섞으면 "기초디자인 모의시험"을 표현할 수 없고, F-15 참고작 추천과 성장 리포트에서 "같은 유형의 모의시험 작품끼리 비교" 같은 질의가 불가능해집니다. 프론트의 기존 필터 칩(전체 / 기초디자인 / 모의시험 / 개인 연습)은 칩마다 쿼리 파라미터를 매핑하면 그대로 유지됩니다 ([frontend-integration-v0.5.1.md §3](frontend-integration-v0.5.1.md)).

## 4. DB 변경 (리비전 `0005`)

| 테이블 | 컬럼 | 타입 | 기본값 | 제약 |
| --- | --- | --- | --- | --- |
| profiles | practical_type | varchar(20) NULL | — | `ck_profiles_practical_type` |
| artworks | practical_type | varchar(20) NULL | — | `ck_artworks_practical_type` |
| artworks | work_category | varchar(20) NULL | — | `ck_artworks_work_category` |
| artworks | work_status | varchar(20) NOT NULL | `'IN_PROGRESS'` | `ck_artworks_work_status` |
| artworks | completed_at | timestamptz NULL | — | `ck_artworks_completed_has_time` |

- 추가 전용(ADD COLUMN). PostgreSQL 11+에서 NULL 컬럼·상수 기본값 컬럼은 테이블 재작성 없이 적용됩니다.
- 기존 데이터: 프로필·작품 분류는 NULL(미분류), 작품은 모두 `IN_PROGRESS`. FINAL 사진이 있는 기존 작품도 자동 완료하지 않습니다(학생 의사 확인 불가).
- downgrade: 0005가 추가한 컬럼·제약만 제거 (저장된 분류·완료 정보는 사라짐, 기존 행은 보존).
- 제외 기능 테이블은 **건드리지 않습니다**.

### 마이그레이션 순서 · v0.6 충돌 방지

```text
0001 (v0.2 auth) → 0002 (v0.3 운영) → 0003 (v0.4 작품·시험) → 0004 (v0.5 질문 콜·녹음) → 0005 (v0.5.1) = head
```

- v0.6 AI 피드백 리비전: `--rev-id 0006`, `down_revision = "0005"`. 이 PR이 develop에 병합된 뒤 만듭니다.
- 다른 브랜치에서 0005를 먼저 만들었다면 head가 2개가 되므로 나중 쪽이 `down_revision`을 고칩니다 (development-guide.md).
- **개발 DB(Supabase)에는 0005를 승인 없이 적용하지 않습니다.** 프론트엔드 담당자의 0002~0004 적용과 충돌하지 않도록, 0004 적용 확인([supabase-dev-verification.md](supabase-dev-verification.md)) → 승인 → `alembic upgrade 0005` 순서로 진행합니다.

## 5. 제외 기능 테이블 처리 계획

FK 분석(로컬 마이그레이션 DB에서 `pg_constraint` 조회)과 개발 DB 행 수는 [database-design.md §3.19](database-design.md)에 정리했습니다. 요약:

- 유지 테이블 → 제외 테이블로 들어오는 FK: **없음** (제외 테이블은 모두 말단)
- 제외 테이블 → 유지 테이블 NO ACTION FK: `help_requests.artwork_id → artworks`, 각종 `*_by → academy_memberships`. 보존 기간 동안 해당 행의 **물리 삭제**를 막을 수 있으나 현재 API는 소프트 삭제만 사용.
- 2026-11-09 개발 DB 읽기 전용 점검: 10개 테이블 모두 **0행**.

물리 삭제 절차 (별도 승인 필요, 이번 PR 범위 아님):

1. 운영 DB를 포함해 각 환경의 행 수 재확인 (`scripts/verify_dev_environment.py`가 출력)
2. 행이 있으면 보존 여부를 기획과 결정 → 필요 시 CSV 백업
3. 새 리비전(head 다음 번호)에서 말단부터 DROP: `attendance_audit_logs` → `attendance_records` · `personal_todos` · `exam_participants`·`exam_session_stages` → `exam_sessions` → `exam_stage_targets` → `exam_templates` · `help_queue_events` → `help_requests`
4. 같은 커밋에서 ORM 모델·enum 제거, `tests/db/conftest.py`의 TRUNCATE 목록 수정
5. downgrade는 0002~0004의 테이블 정의를 다시 만드는 형태로 작성(데이터는 복구 불가임을 명시)

## 6. 작품 완료 정책

| 상황 | 동작 |
| --- | --- |
| FINAL 사진(ACTIVE) 없이 완료 | 409 `FINAL_PHOTO_REQUIRED` |
| 완료 | `work_status=COMPLETED`, `completed_at=now`, 진행 중이던 PENDING 사진 업로드 취소 |
| 이미 완료된 작품 완료 | 200, 변경 없음 (완료 시각 유지) |
| 완료 후 사진 업로드·교체·삭제·대표 변경 | 409 `ARTWORK_COMPLETED` |
| 완료 후 제목·설명·분류·학원 연결 수정 | 허용 (아카이브 정리용) |
| 완료 후 피드백 녹음 추가·삭제 | 허용 (완성작에 대한 첨삭이 일반적) |
| 완료 후 작품 삭제 | 허용 |
| 작업 재개 `POST /reopen` | `IN_PROGRESS`, `completed_at=null`. 사진 변경 다시 가능 |
| 강사 | 완료 상태 조회만 (완료·재개는 학생 본인만) |

## 8. F-15 참고작 추천 설계 메모 (미구현)

> **F-15는 이번 기획에서 새로 정의된 기능이며 아직 구현되지 않았습니다.** 목표 버전 v0.8. 아래는 v0.5.1에서 데이터 구조를 정할 때 고려한 사항과 구현 시 체크리스트입니다.

정의: 학생의 약점과 유사한 문제를 잘 해결한 참고 작품을 추천한다.

추천에 필요한 입력과 현재 준비 상태:

| 입력 | 출처 | 상태 |
| --- | --- | --- |
| 작품 이미지 | `artwork_photos` (FINAL 대표 사진) | ✅ v0.4 |
| 실기 유형 | `artworks.practical_type`, `profiles.practical_type` | ✅ v0.5.1 |
| 작품 메타데이터 | `work_category`, `work_status`/`completed_at`, `work_date`, 단계 사진 | ✅ v0.5.1 |
| 약점 카테고리 | 첨삭 음성 STT → AI 분류 → 강사 확인 (`weakness_tags`, `student_weaknesses` 설계안) | ⏳ v0.6~v0.7 |
| "잘 해결함" 신호 | 강사 확인된 피드백의 긍정 평가, 완료 작품, (선택) 강사 추천 표시 | ⏳ v0.6~v0.7 |
| 공개·사용 동의 | 작품을 다른 학생의 참고작으로 쓰는 것에 대한 **작품별 동의** | ❌ 미설계 |

설계 원칙:

1. **동의가 먼저**: 다른 학생의 작품을 보여 주므로 작품 소유자의 명시적 동의가 필요합니다. 녹음 동의(`recording_consents`)와 같은 버전 관리·철회 가능 구조로 `artwork_share_consents`(또는 `artworks.reference_opt_in` + 동의 이력)를 설계하고, 미성년자는 법정대리인 동의를 고려합니다. 철회 시 추천 후보·캐시에서 즉시 제외.
2. **노출 범위 단계화**: 같은 학원 내 → 플랫폼 전체(익명). 작성자 이름·학원명은 기본 비공개.
3. **추천 근거 저장**: 왜 추천했는지(일치한 약점 태그, 실기 유형, 유사도 점수, 모델/프롬프트 버전)를 `reference_recommendations`에 남겨 설명 가능성·품질 평가·피드백 루프에 사용.
4. **후보 필터 → 순위화 2단계**: (1) 동의된 COMPLETED 작품 중 같은 `practical_type`, 대상 약점 태그가 "해결됨"으로 확인된 작품을 SQL로 거르고 (2) 이미지 임베딩 유사도·약점 일치도로 순위화. 후보 쿼리를 위해 그때 `(practical_type, work_status)` 부분 인덱스와 임베딩 저장소(pgvector 등)를 추가합니다 (현재는 데이터가 적어 인덱스 미추가).
5. **커뮤니티 연동**: 커뮤니티 게시 작품을 후보로 쓸지는 v0.8에서 검토. 커뮤니티 공개 ≠ 참고작 사용 동의로 분리합니다.
6. **품질 지표**: 추천 클릭·저장, 이후 같은 약점의 재발 감소를 추적해 v0.7 성장 리포트와 연결.

## 10. 남은 위험 · 확인 필요

- 수업 일정·수업 주제 API 유지 여부: 기획 확인 필요 (현재 유지).
- `SUPABASE_ANON_KEY`가 백엔드 `.env`에 비어 있어 개발 서버에서 사진·녹음 업로드 API가 503 `STORAGE_NOT_CONFIGURED`입니다 → [supabase-dev-verification.md §2](supabase-dev-verification.md).
- 제외 테이블의 NO ACTION FK는 향후 계정·학원 물리 삭제(탈퇴 처리) 구현 시 장애 요인이 되므로, 탈퇴 기능 전에 물리 삭제 리비전을 진행하는 것이 좋습니다.
- 운영 DB 상태는 확인하지 않았습니다 (운영 DB 접근 금지).
